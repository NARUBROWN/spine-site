# v0.7.0 미리보기 핸들러 입력 전환

Spine `v0.7.0-preview.1`부터 경로, 쿼리와 헤더를 각각 구조체 포인터로 받고 필드에 직접 접근할 수 있습니다. 기존 앱의 입력 인자를 이 방식으로 전환하는 절차를 설명합니다.

::: warning 미리보기 버전과 호환성
이 페이지는 정식 `v0.6.5`에 그대로 적용할 수 없는 미리보기 API를 설명합니다. `query.Values`, `header.Values`, `query.Pagination`과 `path.Int`, `path.String`, `path.Boolean`은 `v0.7.0-preview.1`부터 Deprecated입니다. 기존 방식은 전환 기간에 유지하지만 한 핸들러에서 새 Path, Query, Header DTO와 혼용할 수 없습니다. 제거 버전은 정해지지 않았습니다.
:::

## 적용 버전 {#versions}

| 모듈 | 이 문서에서 사용하는 태그 | 역할 |
| --- | --- | --- |
| `github.com/NARUBROWN/spine` | `v0.7.0-preview.1` | 입력 DTO 계약과 런타임 OpenAPI |
| `github.com/NARUBROWN/spine-echo-platform` | `v0.2.0-preview.1` | HTTP 본문 바인딩, Host와 JSON null 처리 |
| `github.com/NARUBROWN/spine-validator-playground` | `v0.2.0-preview.1` | 선택적 검증과 상세 명세 설명 |

코어와 Echo는 Go 1.25.5 이상, playground를 사용하는 아래 예제는 Go 1.26 이상이 필요합니다. WebSocket이나 이벤트 플랫폼도 함께 사용한다면 해당 플랫폼의 `v0.2.0-preview.1`을 선택하세요.

프로젝트 생성 절차는 [첫 번째 앱](/ko/learn/getting-started/first-app)을 따릅니다. 현재 문서의 CLI `v0.4.2`와 `platform-contracts-v0.6.5` 레시피는 안정 버전을 선택합니다. 새 미리보기 전용 CLI 옵션이나 레시피가 있다고 가정하지 마세요. 기존 앱의 모듈 경로, 엔트리포인트와 composition은 유지하면서 `go.mod`가 있는 위치에서 의존성을 명시적으로 고정합니다.

```bash
go get github.com/NARUBROWN/spine@v0.7.0-preview.1 github.com/NARUBROWN/spine-echo-platform@v0.2.0-preview.1 github.com/NARUBROWN/spine-validator-playground@v0.2.0-preview.1
```

아래 예제는 playground를 사용합니다. 검증기를 사용하지 않는 앱은 기존 검증기 설정을 유지할 수 있습니다. 새 DTO의 타입 변환은 검증기 없이도 수행하지만 `validate` 태그를 검사하지 않으며 OpenAPI는 경로 중심 정보만 제공합니다.

::: tip 문서 UI는 미리보기 2부터 제공
이 페이지의 입력 DTO와 JSON 명세 예제는 `v0.7.0-preview.1`부터 사용할 수 있습니다. `boot.OpenAPIOptions.UI`로 Swagger UI나 ReDoc을 등록하려면 코어를 `v0.7.0-preview.2`로 올리세요. Echo와 playground는 위 표의 `v0.2.0-preview.1`을 사용합니다.

```bash
go get github.com/NARUBROWN/spine@v0.7.0-preview.2
```

[임베드 UI 등록과 부팅 옵션](/ko/reference/api/openapi#tools)을 참고하세요.
:::

## 기존 인자와 새 DTO의 대응 {#mapping}

| 기존 입력 | 새 입력 | 핸들러 안에서 읽는 방법 |
| --- | --- | --- |
| `id path.Int`와 `id.Value` | `path:"user_id"` 필드가 있는 `*UserPath` | `p.UserID` |
| `path.String`, `path.Boolean` | 이름과 값 타입을 선언한 Path DTO 필드 | 일반 필드 접근 |
| `q query.Values` | `query` 태그가 있는 `*UserQuery` | `q.Page`, `q.Tags` |
| `page query.Pagination` | Query DTO의 `Page`, `Size` 필드 | 누락 시 앱에서 기본값 적용 |
| `headers header.Values` | `header` 태그가 있는 `*UserHeaders` | `headers.RequestID` |
| 기존 본문 DTO | 별도의 본문 구조체 포인터 유지 | `body.Name` |

경로, 쿼리, 헤더의 입력 필드를 하나의 구조체에 섞지 않습니다. `path` 태그는 라우트 변수 이름과 대소문자까지 정확히 연결합니다. 인자의 이름이나 구조체 필드 순서로 경로를 배정하지 않습니다.

## 새 핸들러의 전체 예제 {#example}

다음은 입력 선언과 동작을 함께 확인하는 독립 참고 앱의 `main.go`입니다. 기존 앱에서는 DTO, 핸들러와 부팅 설정을 현재 composition에 반영하세요. `app.Route`와 생성자 등록 API는 그대로 사용합니다.

```go
package main

import (
    "log"

    "github.com/NARUBROWN/spine"
    echoplatform "github.com/NARUBROWN/spine-echo-platform"
    playground "github.com/NARUBROWN/spine-validator-playground"
    "github.com/NARUBROWN/spine/pkg/boot"
    "github.com/NARUBROWN/spine/pkg/httpx"
)

type UserPath struct {
    UserID int64 `path:"user_id" validate:"gt=0"`
}

type UserQuery struct {
    Page *int     `query:"page"`
    Size *int     `query:"size"`
    Tags []string `query:"tags"`
}

type UserHeaders struct {
    RequestID string `header:"X-Request-ID" validate:"required"`
    Host      string `header:"Host"`
}

type UpdateBody struct {
    Name  string `json:"name" validate:"required"`
    Count int    `json:"count" validate:"gte=0"`
}

type UserView struct {
    ID        int64    `json:"id"`
    Name      string   `json:"name"`
    Count     int      `json:"count"`
    Page      int      `json:"page"`
    Size      int      `json:"size"`
    Tags      []string `json:"tags"`
    RequestID string   `json:"request_id"`
    Host      string   `json:"host"`
}

type UserController struct{}

func (*UserController) Update(body *UpdateBody, p *UserPath, q *UserQuery, headers *UserHeaders) httpx.Response[UserView] {
    page, size := 1, 20
    if q.Page != nil {
        page = *q.Page
    }
    if q.Size != nil {
        size = *q.Size
    }
    return httpx.Response[UserView]{Body: UserView{
        ID: p.UserID, Name: body.Name, Count: body.Count,
        Page: page, Size: size, Tags: q.Tags,
        RequestID: headers.RequestID, Host: headers.Host,
    }}
}

func main() {
    engine, err := playground.New()
    if err != nil {
        log.Fatal(err)
    }
    app := spine.New(echoplatform.Option(), spine.WithValidator(engine))
    app.Constructor(func() *UserController { return &UserController{} })
    app.Route("POST", "/users/:user_id", (*UserController).Update)
    options := boot.Options{
        Address: ":8080",
        EnableGracefulShutdown: true,
        HTTP: &boot.HTTPOptions{
            OpenAPI: boot.OpenAPIOptions{Enabled: true},
        },
    }
    if err := app.Run(options); err != nil {
        log.Fatal(err)
    }
}
```

필수 여부는 등록한 validator의 계약으로 판단합니다. 위 예제의 `Name`과 `RequestID`는 `validate:"required"`로 필수이며, 포인터인지 여부만으로 필수를 정하지 않습니다. `Page`와 `Size`의 포인터는 누락과 실제 숫자 `0`을 구분합니다. 양수나 최대 크기 같은 규칙은 앱이 validator에 별도로 선언해야 합니다.

의존성을 고정하고 코드를 반영한 뒤 프로젝트 루트에서 실행합니다. 참고 앱은 해당 파일을 단독 실행할 수 있고, 기존 앱은 현재 엔트리포인트를 사용합니다.

```bash
go mod tidy
go run main.go
```

## 한 핸들러씩 함께 전환하기 {#compatibility}

| 조합 | 미리보기에서의 처리 |
| --- | --- |
| 기존 입력 API만 사용 | Deprecated 시그니처 유지. Pagination의 반복 page/size는 HTTP 400 |
| 기존 입력과 기존 본문 DTO 또는 context | 계속 지원 |
| 새 Path, Query, Header DTO와 본문 DTO 또는 context | 지원 |
| Deprecated 입력과 새 Path, Query, Header DTO를 한 핸들러에서 혼용 | 출처가 달라도 부팅 거부 |
| 서로 다른 핸들러에서 각각 기존 API와 새 DTO 사용 | 지원 |

예를 들어 경로만 `*UserPath`로 바꾸고 같은 핸들러에 `query.Values`나 `query.Pagination`을 남기면 안 됩니다. 그 핸들러의 Deprecated 입력 인자를 모두 함께 전환하세요. `context.Context`와 컨트롤러 컨텍스트는 Deprecated 입력이 아니며 그대로 주입할 수 있습니다.

새 Path DTO와 기존 path 래퍼를 섞으면 `HTTP_PATH_INPUT_MIXED`, 그 밖의 혼용은 `HTTP_INPUT_API_MIXED`입니다. 같은 DTO 타입을 중복 인자로 선언하면 `HTTP_INPUT_DTO_DUPLICATED`, 여러 본문 DTO는 `HTTP_BODY_PARAMETERS_DUPLICATED`, 서로 다른 DTO 인자에서 같은 출처의 키가 중복되면 `HTTP_INPUT_KEY_DUPLICATED`로 부팅 전에 거부합니다. 한 Query, Header, Path DTO 내부의 입력 키 중복은 `HTTP_INPUT_CONTRACT_INVALID`입니다. 같은 DTO를 다른 핸들러에서 재사용하는 것은 허용합니다.

Query, Header, Path DTO의 공개 필드에는 해당 출처 태그를 지정하거나 `query:"-"`처럼 명시적으로 제외합니다. `param`은 `path`의 별칭이 아닙니다. Query 또는 Header DTO의 `json` 태그는 직렬화 이름으로 함께 둘 수 있지만 입력 출처를 본문으로 바꾸지 않습니다.

## 값과 바인딩 동작의 차이 {#binding}

| 입력 | 기존 조회 방식 | 새 구조체 입력 |
| --- | --- | --- |
| 누락된 page와 size | Pagination 기본값 `1`, `20` | 포인터는 `nil`, 예제 핸들러가 `1`, `20` 적용 |
| 잘못된 숫자 | `Values.Int`와 Pagination은 기본값 사용 | HTTP 400, 기본값으로 대체하지 않음 |
| 숫자 `0` 또는 bool `false` | 조회 메서드의 동작 유지 | 값의 존재와 validator의 값 제약을 구분 |
| 반복 쿼리와 쉼표 목록 | Values 조회 메서드는 첫 번째 값 사용 | 슬라이스는 반복 키와 쉼표 구분을 함께 처리 |

`?tags=a,b&tags=c`는 `["a","b","c"]`가 되고, `?tags=a,%20b`는 `["a"," b"]`가 됩니다. 공백, 빈 원소와 중복을 임의로 제거하지 않습니다. 새 bool 필드는 `strconv.ParseBool`을 사용하므로 기존 조회가 받던 `yes`, `on` 같은 표기를 그대로 허용하지 않습니다.

기존 `query.Pagination`도 미리보기에서는 `?page=1&page=2`처럼 `page` 또는 `size`가 반복되면 HTTP 400을 반환합니다. 안정 버전이 첫 값을 읽던 동작과 다릅니다. 반복되지 않은 값의 파싱 실패와 누락에는 기존 기본값을 유지합니다.

경로 구간은 생략할 수 없습니다. Path DTO의 포인터 필드도 경로를 선택적으로 만들지 않으며 `path` 이름이 라우트에 없으면 부팅 시 거부합니다.

일반 값 타입에 명시적인 JSON `null`을 보내면 `0`, `false`나 빈 문자열로 바꾸지 않고 HTTP 400으로 거부합니다. 누락된 필드와 포인터, map, slice의 `null`은 별도로 취급하며 등록한 validator가 최종 허용 여부를 판단합니다. 사용자 정의 `json.Unmarshaler`는 자체 null 처리를 결정합니다. 코어의 WebSocket과 소비자 JSON DTO에도 같은 값 타입 규칙이 적용됩니다.

Echo 미리보기의 기본 본문 바인딩은 경로와 URL 쿼리를 본문 DTO에 병합하지 않습니다. 폼도 본문 값만 읽습니다. 기존에 이런 병합에 의존했다면 출처별 DTO로 분리하세요. 사용자 지정 Binder는 해당 구현의 계약을 따릅니다.

`header:"Host"`는 Go 요청의 `Request.Host`에서 읽으며 포트도 유지합니다. `X-Forwarded-Host`를 대신 사용하지 않습니다. 헤더 목록은 쿼리와 문법이 다르므로 Authorization, Cookie, Host 등에 일반 슬라이스를 선언하지 말고 문자열이나 적절한 사용자 타입을 사용하세요.

## 요청으로 확인하기 {#verify}

앱이 실행된 상태에서 다음 요청을 보냅니다.

```bash
curl -i -X POST 'http://localhost:8080/users/42?tags=a,b&tags=c' -H 'Content-Type: application/json' -H 'X-Request-ID: preview-check' --data '{"name":"Ada","count":0}'
curl -i -X POST 'http://localhost:8080/users/42?page=bad' -H 'Content-Type: application/json' -H 'X-Request-ID: preview-check' --data '{"name":"Ada","count":0}'
curl -i -X POST 'http://localhost:8080/users/42' -H 'Content-Type: application/json' -H 'X-Request-ID: preview-check' --data '{"name":"Ada","count":null}'
curl -i -X POST 'http://localhost:8080/users/42' -H 'Content-Type: application/json' --data '{"name":"Ada","count":0}'
curl -i http://localhost:8080/openapi.json
```

첫 요청은 HTTP 200이며 응답의 `id`는 `42`, `page`는 `1`, `size`는 `20`, `tags`는 `["a","b","c"]`입니다. 잘못된 page, 일반 int에 보낸 null, 필수 헤더 누락은 각각 HTTP 400입니다. 형식 변환에 실패한 DTO는 해당 validator와 핸들러에 전달하지 않습니다. 인자는 순서대로 해석하므로 앞선 DTO의 검증은 이미 실행됐을 수 있습니다. 검증 오류의 `fields[].in`은 `body`, `path`, `query`, `header` 출처를 구분합니다.

마지막 요청은 명시적으로 활성화한 OpenAPI JSON을 반환합니다. 핸들러 안에서 적용한 page와 size 기본값은 명세 생성기가 추론하지 않습니다. 상세 설정과 한계는 [런타임 OpenAPI API](/ko/reference/api/openapi)를 참고하세요.
