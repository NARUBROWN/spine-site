# Spine 기업 도입 지원 운영 기준 초안 v0.1

기업 수 제한 없음, 무상 지원, 24/7 문의 접수, 가용 시간에 개발자 직접 대응을 고정 원칙으로 둔다. 공개 안내 페이지는 `/ko/enterprise-support`이며, 공식 문의 창구는 Spine 공식 저장소의 GitHub Issues다. 공식 README와 같은 이슈 작성 주소를 사용한다.

## 신청과 지원의 기본 원칙

| 항목 | 기준 |
| --- | --- |
| 신청 대상 | Spine 도입을 검토하거나 사용 중인 기업과 개발팀 |
| 모집 | 기업 수 제한 없이 상시 접수 |
| 지원 비용 | 아래 범위의 상담과 기술 지원은 무상 |
| 접수 시간 | 24시간, 주말과 공휴일 포함 |
| 실제 대응 | 개발자가 가용 시간에 확인하고 우선순위에 따라 대응 |
| 응답 기한 | 고정 응답 시간과 복구 시간은 보장하지 않음 |
| 진행 방식 | 글, 코드, 로그를 통한 비동기 지원이 기본이며 필요하면 미팅 일정 협의 |
| 지원 기간 | 일률적인 종료 기간 없이 문의 단위로 진행 |

기업은 언제든 신청할 수 있다. 실제 작업은 확인 가능한 범위부터 착수하고 나머지는 대기 상태로 관리한다.

## 지원 범위와 완료 기준

제품 DX의 기준은 Spring과 NestJS의 비즈니스 아키텍처와 개발 경험을 Go로 이어 가는 것이다.

| 지원 유형 | 제공하는 내용 | 해당 문의의 완료 기준 |
| --- | --- | --- |
| 도입 상담 | 서비스 특성 검토, 적용 가능 범위와 필요한 작업 설명 | 적용 방향과 다음 단계가 정리됨 |
| 아키텍처 상담 | Controller, Service, Repository, DI, 인터셉터, 오류 처리 등의 대응 설계 | 질문한 구조에 대한 권장안과 이유가 전달됨 |
| 초기 적용 지원 | 설정, 등록, 실행 문제 확인, 대표 기능이나 관련 코드 검토 | 적용 방법이 확인되거나 실행을 막는 원인이 정리됨 |
| 오류 대응 | 재현 확인, 원인 분석, 우회 방법과 프레임워크 수정 검토 | 수정이나 우회 방법을 검증하거나 후속 작업으로 명확하게 연결됨 |
| 개선 제안 | 사용성, 문서, 예제, 신규 기능 의견 검토 | 반영, 추가 검토, 보류 여부와 이유가 전달됨 |

기업 개발팀은 업무 기능 구현과 서비스 운영을 맡고, Spine 측은 도입 방향, 프레임워크 사용, 연동 문제 해결을 지원한다.

전체 프로젝트 구현, 상시 운영 대행, 장기간의 기업 전용 기능 개발은 별도 범위 협의가 필요하다. 코드 리뷰는 문의와 관련된 기능과 변경 부분을 기준으로 진행한다.

## 실제 영향에 따른 우선순위

| 우선순위 | 판단 기준 | 처리 원칙 |
| --- | --- | --- |
| 긴급 | 운영 서비스의 핵심 기능이 중단됐거나 데이터 정합성 문제가 발생 중 | 확인한 문의 중 가장 먼저 원인 분리와 우회 방법 검토 |
| 적용 차단 | 빌드, 기동, 핵심 기능 오류로 도입이나 개발 진행이 막힘 | 재현 정보가 갖춰지면 일반 상담보다 우선 처리 |
| 일반 | 사용법과 설계 질문, 우회 가능한 오류, 코드 검토 | 기본적으로 접수 순서에 따라 처리 |
| 개선 제안 | 신규 기능, 편의성 개선, 도입을 막지 않는 문서와 예제 제안 | 관련 작업과 묶어서 검토 |

운영 영향, 우회 가능성, 다른 사용자에게도 발생하는 문제인지를 함께 보고 조정한다. 배포 일정이 급하다는 사정만으로 긴급 장애와 같은 순위가 되지는 않는다.

원인이 아직 밝혀지지 않은 운영 장애도 우선 확인할 수 있다. 앱 코드나 외부 인프라 문제로 판명되면 확인한 근거와 다음 조치를 안내하는 데까지 지원한다.

## 접수 정보

도입 상담은 세 가지 정보로 시작한다.

- 어떤 서비스에 Spine을 적용하려는지
- 현재 사용하는 기술과 옮기려는 범위
- 궁금한 점 또는 막힌 부분

오류 문의에는 다음 정보를 추가로 요청한다.

- Spine과 Go 버전 및 실행 환경
- 기대한 동작과 실제 동작
- 재현 방법, 관련 코드 또는 오류 로그
- 운영 영향과 현재 가능한 우회 방법

처음부터 긴 신청서를 요구하지 않는다. 필요한 정보가 빠졌으면 확인 과정에서 요청한다. 기업 내부 코드 전체를 공유하기 어려우면 축소한 재현 코드로 진행한다.

## 처리 상태와 종료 결과

관리 상태는 네 개로 유지한다.

| 상태 | 의미 |
| --- | --- |
| 접수·대기 | 문의가 들어왔고 확인 또는 착수를 기다림 |
| 확인·진행 중 | 상담, 재현, 분석, 수정 등을 진행 중 |
| 추가 정보 대기 | 문의자의 답변이나 외부 확인이 필요함 |
| 완료 | 답변 또는 조치를 마치고 결과를 기록함 |

처리를 시작하면 확인한 내용, 추가로 필요한 정보, 다음 행동을 짧게 알린다. 원인 발견, 우회 방법 확보, 패치 제공처럼 의미 있는 변화가 있을 때 업데이트한다.

완료 상태의 결과는 다음과 같이 구분해 기록한다.

| 완료 결과 | 기준 |
| --- | --- |
| 해결 | 수정이나 우회 방법으로 문제가 해소된 것을 확인 |
| 안내 완료 | 상담, 설계, 사용법 질문에 필요한 답변 제공 |
| 후속 추적 | 원인이나 다음 작업은 정리됐지만 문제가 남아 있음 |
| 종료 | 요청 철회, 중복, 지원 범위 밖 등의 사유로 마침 |

패치 계획만 세웠거나 답변만 보낸 오류를 해결로 기록하지 않는다. 후속 추적은 남아 있는 문제와 연결된 다음 작업을 기록한다.

추가 정보 요청 후 14일 이상 답변이 없으면 다음 정리 시 보류하고, 정보가 오면 이어서 진행한다. 네 상태를 유지하기 위해 상태는 추가 정보 대기로 두고 보류 여부와 사유를 별도로 기록한다.

## 혼자 운영할 때의 내부 기준

- 문의는 공식 창구 한 곳으로 모으고 다른 채널에서 온 문의도 그곳에 기록한다.
- 한 문의에서는 해결할 문제 하나를 명확히 잡는다.
- 미팅은 글과 코드만으로 해결하기 어려울 때, 30분 내외로 일정을 협의한다.
- 같은 원인의 문의는 묶어서 처리하고 공통 답변은 문서와 예제로 남긴다.
- 기능 추가와 큰 수정은 즉시 반영을 약속하지 않고 검토 결과와 가능한 다음 단계를 안내한다.
- 지원 버전은 최신 정식 릴리스를 우선 확인하고 구버전은 사용 환경과 재현 여부를 보고 판단한다.
- 대기량이 늘면 착수가 지연되고 있음을 안내한다.

기업 사례 공개는 지원과 분리해서 동의를 받는다. 기업명, 로고, 코드, 성과 수치는 승인받은 범위만 사용한다.
